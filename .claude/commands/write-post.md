사용자가 작성한 초안을 jihoon 스타일의 기술 블로그 글로 정리해주세요.

## 작업 순서

1. 사용자의 초안을 읽고 **핵심 주제와 논지**를 파악합니다.
2. 주제와 관련된 **최신 기술 동향, 레퍼런스, 사례**를 웹 검색으로 리서치합니다.
3. 초안 내용과 리서치 결과를 결합하여, 아래 "문체 가이드"에 따라 글의 구조, 톤, 표현을 다듬습니다.
4. 결과물을 `content/` 디렉토리의 적절한 날짜 폴더에 마크다운으로 작성합니다.

## 리서치 가이드

- 초안에 포함된 기술적 주장(성능 수치, 비교, 동작 원리 등)의 **사실 관계를 검증**합니다.
- **리서치는 항상 현재 시점(프롬프팅 시점) 기준으로 수행한다.** 글이 과거에 작성되었더라도 최신 버전, 현재 생태계 현황, 최근 변경사항을 기준으로 조사한다.
- 주제와 관련된 **최신 버전, 변경사항, 생태계 현황**을 조사하여 글의 시의성을 확보합니다.
- 업계 전문가의 발언, 공식 문서, 벤치마크 등 **레퍼런스 기반 서술**에 활용할 자료를 수집합니다.
- 리서치 결과 중 초안에 없던 내용이라도, 주제의 깊이를 더하거나 독자에게 유용한 맥락이라면 적극 반영합니다. (단, 지면에서 차지하는 비중은 아래 "글의 깊이 가이드"를 따릅니다. 출처를 많이 붙이는 것과 글이 깊어지는 것은 다릅니다)
- 기술 용어의 정확한 정의를 확인하되, 영어가 더 정확하고 검색하기 쉬운 용어는 번역하지 않습니다. 첫 등장 풀이는 독자의 이해를 실제로 돕는 경우에만 붙입니다.
- **모든 기술적 주장은 검증된 자료와 출처에 근거해야 한다.** 확인되지 않은 내용은 추측임을 명시하거나 제외한다.

## 쓰면서 배우는 글쓰기

[Sean Goedecke의 "Blog about things you don't understand yet"](https://www.seangoedecke.com/blog-about-things-you-dont-understand-yet/)에서 가져온 핵심은 완성된 지식을 설명하는 척하지 않고, 글쓰기를 조사와 사고의 도구로 쓰는 것이다.

1. 시작 전에 **알고 싶은 질문**, **초기 가설**, **합리적인 독자가 반론할 수 있는 핵심 주장**을 각각 한 문장으로 적는다. 단순 요약이나 누구도 이견이 없는 초안이면 질문을 더 좁힌다.
   - 글 전체의 핵심 주장 한 문장과 각 절에서 독자가 얻어야 할 내용 한 문장도 편집 메모로 정리한다.
   - 이 편집 메모는 원고를 검증하기 위한 것이며 공개 마크다운에 자동으로 넣지 않는다.
2. 기술 해법보다 먼저 **원래 어떤 문제가 있었는지** 설명한다. 독자가 분야의 중요성을 이미 안다고 가정하지 않는다.
3. 조사 메모와 본문에서 **확인된 사실**, **사실에서 끌어낸 추론**, **필자의 의견**을 구분한다. 반례와 가장 강한 반론을 찾아 핵심 주장을 다시 검증한다.
4. 쓰는 동안 생각이 바뀐 지점, 틀렸던 가정, 아직 확인하지 못한 부분을 기록한다. 결론이 초기 가설과 달라져도 초안을 억지로 원래 방향에 맞추지 않는다.
5. 결론까지 쓴 뒤 도입을 다시 쓴다. 초고의 결론이 도입보다 더 정확하고 압축되어야 하며, 그렇지 않거나 새로 배운 것이 없다면 발행 가치와 질문을 재검토한다.
6. 자신의 경험과 전문성 범위를 밝힌다. 학습 중인 주제에서는 권위자인 척하지 않고, 독자가 검증할 수 있도록 근거와 한계를 함께 남긴다.

## 글의 깊이 가이드

외부 자료를 많이 붙인다고 글이 깊어지지 않는다. 깊이는 **필자가 직접 겪고 재본 것**에서 나오고, 외부 자료는 그것을 해석하는 도구다. 외부 인용이 지면을 지배하면 다른 글의 재탕이 된다.

### 1차 자료를 먼저 턴다

글을 쓰기 전에 이 리포와 계정 안에 있는 실제 자료부터 확인한다. 웹 검색은 그다음이다.

- **리포**: PR 본문의 측정 표, 커밋, 소스 코드, 테스트, `CLAUDE.md`에 적힌 실측 기록
- **Search Console**: `.gsc-data/`의 CSV 4종 (`pnpm gsc`로 갱신). 실제 쿼리, 노출, 클릭, 순위
- **Sentry**: MCP로 `hooninedev/jihoon-blog` 프로젝트의 이슈와 이벤트를 직접 조회. 태그 분포, 릴리스, 발생 시각까지 확인 가능
- **빌드**: 번들 크기, 산출물 용량 같은 값은 직접 재서 쓴다

### 필자의 배경을 반영한다

필자는 **회사에서 Sentry 기반 에러 모니터링을 오래 써왔고**, 개인 블로그에서는 **Google Analytics, Search Console, SEO**를 직접 운영해왔다. 이 배경을 지운 채 "몰라서 못 했다" 식의 초심자 프레이밍으로 쓰지 않는다. 어려웠던 이유는 대개 지식의 부재가 아니라 **판단(무엇을 실패로 볼지, 어디에 심을지)과 우선순위**에 있었다.

### "어려웠다"는 구체적으로 쓴다

"어렵다"고만 쓰면 글이 얕아진다. 무엇이 왜 어려웠는지를 확인 가능한 수준까지 내린다. 예를 들어 프론트엔드 관측이 어려웠던 이유는 브라우저가 값을 만드는 방식을 알아야 했기 때문이다. `PerformanceObserver`의 `buffered` 옵션 제약, CLS의 세션 윈도우 규칙, iframe 때문에 라이브러리 값과 CrUX 값이 갈리는 문제처럼 **문서로 확인되는 구체적 장벽**을 짚는다. 그리고 AI가 그중 무엇을 덜어줬고 무엇은 여전히 사람의 판단인지를 나눠서 쓴다.

### "고쳤다"고 쓰기 전에 다시 조회한다

과거의 작업을 글로 정리할 때는 **지금 상태를 반드시 다시 확인한다.** 고쳤다고 믿고 쓴 결말이 실제로는 틀린 경우가 있었다. (관측 글에서 실제로 발생했다. 타임아웃 수정 후에도 같은 계열의 이슈가 계속 쌓이고 있었고, 그 사실이 오히려 글의 가장 좋은 부분이 됐다) 확인 결과가 예상과 다르면 그것을 숨기지 말고 미해결 상태 그대로 쓴다. 가설은 가설이라고 명시한다.

## 문체 가이드 (jihoon 스타일)

### 톤과 어조
- **한다체(해체)** 사용: "~한다", "~이다", "~것이다"
- 1인칭은 **"필자"**를 일관되게 사용 ("나" 대신)
- 기본 톤은 **차분하고 논리적**이며, 괄호 안에는 필자의 실제 소견이나 견해를 담는다.
  - 괄호 안 내용은 글과 동떨어진 농담이나 밈이 아니라, 본문 흐름에서 자연스럽게 이어지는 필자의 생각이어야 한다.
  - 예: `(이 부분이 처음엔 가장 헷갈렸다)`, `(실제로 적용해보니 이 순서가 결정적이었다)`
  - 지양: 본문과 무관한 썰렁한 농담, 인터넷 밈/속어의 과도한 사용
- **양보-주장 구조**를 활용: "물론 ~이지만, 필자 생각은 다르다"

### 도입부 패턴
1. **선언 문장**: "이번 포스팅에서는 [주제]에 대한 이야기를 해보려고 한다."
2. **개인적 맥락**: 2-3문단에 걸쳐 왜 이 주제를 다루게 되었는지 설명
3. **독자 공감**: 본인이 처음 이 개념을 접했을 때의 경험담으로 시작

### 소제목

- H2와 H3는 본문을 찾기 위한 탐색 표지다. 절의 핵심 개념, 질문 또는 주장을 짧은 명사구나 짧은 문장으로 쓴다.
- 제목만 순서대로 읽어도 문제 제기, 설명, 판단의 흐름이 드러나야 한다.
- 하나의 제목에 여러 주제를 쉼표나 접속사로 묶지 않는다.
- 추상적인 비유보다 본문에서 실제로 설명하는 단어를 우선한다.
- 길이를 기계적으로 제한하지 않되 모바일 목차에서 한눈에 읽히는 수준을 우선한다.
- 제목과 첫 문단은 같은 문장을 반복하지 않고 서로 보완한다.
- h2, h3 두 단계까지만 사용한다.
- 초안이 끝나면 H2와 H3만 따로 읽어 절 구분, 논리 순서, 본문 범위와의 일치를 검토한다.

### 주제 전환
- 직전 섹션의 결론을 **질문으로 변환**해서 다음 섹션으로 연결
  - 예: "그렇다면 지금 우리는 어떤 방향으로 미래를 준비해야 할까?" -> 다음 섹션
- "여기까지 읽으면 자연스럽게 떠오르는 질문이 하나 있다."
- 섹션과 섹션 사이의 흐름은 독자가 어색함을 느끼지 않도록 **문맥적으로 자연스럽게** 이어져야 한다.

### 기술 개념 설명
- **정확성과 검색 가능성을 우선**: 제품명, API, SDK, 코드 식별자와 업계에서 영어가 더 명확한 용어는 원문을 보존한다. `Computer Science`, `wall-clock time`, `OpenTelemetry`를 어색한 직역으로 바꾸지 않는다.
- **첫 등장 풀이는 선택**: 독자의 이해를 실제로 돕는 경우에만 `wall-clock time(실제 경과 시간)`처럼 한 번 설명한다. 설명이 의미를 좁히거나 문장을 무겁게 만들면 영어만 쓴다.
- 기술 용어 기준은 `content/terminology.yml`을 확인하고, 발행 전에 `pnpm content:terms`를 실행한다.
- 본문 흐름 안에서 짧은 해설이 필요한 핵심 용어는 `:term[RUM]{key="rum"}` 형식으로 표시한다.
  - 해당 절을 이해하는 데 필요한 용어만 표시하고, 같은 절에서는 첫 의미 있는 등장에만 쓰는 것을 기본으로 한다.
  - `key`는 `content/glossary.json`에 있는 소문자 kebab-case 식별자를 사용한다.
  - 용어 해설에만 핵심 논리를 넣지 않는다. 설명 패널을 열지 않아도 본문을 이해할 수 있어야 한다.
  - 운영 글은 `pnpm content:glossary`, 관측 시리즈 연구 초안은 `pnpm content:glossary -- --drafts`로 검증한다.
- **비유와 메타포를 적극 활용**: 개발자가 직관적으로 이해할 수 있는 비유 사용
  - 예: "작업 기억은 일종의 고정 크기 스택이라고 볼 수 있다"
- 비유 후에는 **한계를 짚어주기**: "다만 실제로는 ~이기 때문에..."
- 학술 논문, RFC 등 **레퍼런스 기반 서술** 선호
- 출처를 본문에 언급할 때는 자료의 세부 내용보다 **누가(저자, 기관, 집단) 이 자료를 만들었는지**를 중심으로 소개한다.
  - 예: "Stanford 연구팀(Liu et al.)은...", "React 코어팀의 Andrew Clark은..."
  - 지양: 논문 제목이나 arXiv ID를 본문에 장황하게 나열하는 것

### 문장 구조
- **긴 설명문 + 짧은 단문의 리듬감**: 2-3문장 설명 후 "이런 상황인 것이다."로 마무리
- **질문형 문장**을 전환 장치로 적극 사용
- **"~것이다", "~인 것이다"** 문미를 활용해 단정적이면서도 설명적인 뉘앙스
- 1문단 = 1-3문장, 문단 사이 빈 줄로 여유롭게
- **가독성과 인식의 흐름**을 최우선으로 한다. 독자가 읽다가 흐름이 끊기거나 어색함을 느끼는 지점이 없어야 한다.

### 마크다운 문법 규칙
- 강조는 `**텍스트**` (볼드)만 사용한다. `*텍스트*` (이탤릭)는 사용하지 않는다.
  - 한글은 이탤릭 렌더링이 자연스럽지 않아 시각적 효과가 약하다.
  - 톤 전환이나 부연은 괄호 안 코멘트로 처리한다.
- 인라인 코드(`` `코드` ``)는 실제 코드, 파일명, API 이름 등 기술 요소에만 사용한다.
- **em dash(—)나 하이픈(-)을 문장 이음, 설명 연결, 제목·부제 구분 용도로 사용하지 않는다.** 본문·소제목·목록·프론트매터(seoTitle 등)·`:::ref` 링크 텍스트 어디에서도 마찬가지다. 대신 쉼표, 콜론(`:`), 마침표, 또는 자연스러운 문장 구조로 표현한다.
  - **예외: 외부 원문을 그대로 싣는 인용 블록.** 원문에 em dash 가 있으면 그대로 둔다. 규칙을 지키려고 원문 구두점을 바꾸면 오인용이 된다. 문장 중간에서 끊을 때는 말줄임표(…)로 생략을 표시한다.
  - 지양: `방향 1 — harness`, `2025년 10월 — Agent Skills`, `Zustand — 소스코드`, `상태를 구독하고 — 변경을 감지한다`
  - 권장: `방향 1, harness` 또는 `방향 1: harness`, `2025년 10월, Agent Skills`, `Zustand 소스코드`, `상태를 구독하고 변경을 감지한다`

### 인용 사용 규칙 (인용 블록은 아껴 쓴다)

인용 블록(`> `)은 논지를 **뒷받침할 때만** 쓴다. 출처가 존재한다는 사실을 증명하려고 붙이는 인용은 글의 밀도를 떨어뜨린다.

- **글 하나에 인용 블록 3~5개를 상한**으로 본다. (기존 글 실측: 대부분 0~3개이고, 8개 이상은 650줄이 넘는 긴 글에서만 나온다. 250줄짜리 글에 11~18개는 과하다)
- 인용 블록을 넣기 전에 자문한다. **이 문장의 표현 자체가 필요한가, 아니면 사실만 필요한가?** 사실만 필요하면 인용하지 말고 인라인 링크를 걸고 필자의 문장으로 푼다.
  - 인용할 가치: 정의를 확정하는 문장, 통념을 뒤집는 문장, 표현 자체가 논지의 축이 되는 문장
  - 인용하지 않을 것: 일반적인 설명, 상식적인 권고, 이미 본문에서 풀어 쓴 내용의 반복
- **인용 블록 사이에는 필자의 문단이 최소 하나 들어가야 한다.** 인용이 곧바로 이어지면 필자의 목소리가 사라지고 남의 문장을 엮은 글이 된다.
- 인용을 걷어낼 때의 기계적 패턴: **인라인 링크는 남기고, 인용 블록만 지우고, 내용을 필자의 문장으로 옮긴다.** 근거의 추적 가능성은 링크가 담당한다.
- 남긴 인용은 원문 그대로 싣고, 바로 다음 문단에서 우리말로 풀어 준다. (기존 글의 방식)

### 시각 자료 가이드 (참조를 쓰기 전에 파일을 만든다)

**플레이스홀더 문법을 쓰지 않는다.** `![설명](그림이나자료필요(AI 이미지 생성 프롬프트: ...))` 형식은 괄호가 중첩돼 마크다운 이미지로 파싱되지 않고, 프롬프트 문구가 본문에 그대로 노출된다. 실제로 발행 대기 중이던 글 두 편에서 이 문제가 있었다.

원칙은 하나다. **이미지 파일을 먼저 만들고, 그다음에 본문에 참조를 쓴다.** 만들 수 없으면 참조도 쓰지 않고 문장으로 설명한다.

**자료의 우선순위**

1. **이 리포와 이 블로그 계정의 실제 데이터로 만든 도표.** 가장 가치가 높다. (`.gsc-data/`의 Search Console CSV, Sentry MCP로 조회한 이슈/이벤트, 빌드 실측값, PR 본문의 측정 표)
2. **개념 다이어그램.** 텍스트로 설명하면 두 문단이 걸리는 구조를 한 장으로 보여줄 때.
3. **외부 스크린샷.** 최후의 선택지다. 남의 화면을 붙이면 설명이 아니라 분량 채우기로 읽힌다. 쓸 경우 출처와 라이선스를 확인하고 본문에 출처를 밝힌다.

**제작 방법 (HTML + 헤드리스 Chrome)**

기존 글의 도표(`260610`, `260611`, `260622`)와 같은 스타일을 유지한다. HTML을 작성해 스크린샷으로 굽는 방식이다.

- 디자인 토큰: 배경 `#17171a`, 카드 `#1f1f24`, 테두리 `#34343d`, 본문 `#e8e8ea`, 보조 텍스트 `#9a9aa2`, 강조 보라 `#a78bfa`, 강조 주황 `#f5a623`
- 구성: 보라색 제목 + 회색 부제 + 본문 도형 + 하단 해설 한두 줄 (해설에서 핵심어만 `<b>`)
- 폰트는 `Pretendard`(로컬에 설치돼 있음), 캔버스 폭은 1200px, 렌더는 2배 스케일
- 렌더 명령
  ```bash
  "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
    --headless --disable-gpu --hide-scrollbars --force-device-scale-factor=2 \
    --window-size=1200,<높이> --screenshot=out.png file://<절대경로>.html
  ```
- 높이는 콘텐츠에 맞춰 지정하고, 렌더한 PNG를 **반드시 눈으로 확인**한다. (잘림과 빈 여백이 자주 생긴다)

**본문에 넣는 방법**

- 파일은 `content/YYMMDD/1.png` 처럼 번호 순으로 저장한다. 본문 등장 순서와 번호를 맞춘다.
- 참조는 `![설명이 담긴 alt](1.png?w=720)` 형식. 가로로 넓은 도표는 `?w=720`, 좁은 도표는 `?w=500` 을 기준으로 하고 그 사이 값도 쓸 수 있다
- 빌드 시 `public/content/`로 자동 복사되므로 따로 옮기지 않는다. (`pnpm build`가 `scripts/copy-content-images.js`를 실행)
- alt 텍스트는 그림이 무엇을 보여주는지 문장으로 적는다. 파일명(`1.png`)을 alt로 쓰지 않는다.
- 글 하나에 1~5장이 적정선이다. 텍스트만으로 구조나 수치 대비를 설명하기 어려운 지점에 넣는다.
- **도표 하단 해설에는 본문 인접 문단에 없는 관찰을 적는다.** 본문 문장을 그대로 옮긴 해설은 지운다. 같은 말을 두 번 읽게 만들고, 도표가 본문의 장식으로 보이게 한다.
- 도표가 뒤 절의 반전이나 결론을 미리 말하지 않게 한다. 그림은 그 자리까지 읽은 독자가 아는 것만 담는다.

### 링크 사용 규칙 (인라인 vs 참고 자료)
- **본문에서 직접 활용(인용)한 출처는 본문에 인라인 링크로 걸고, 하단 참고 자료(`:::ref`)에서는 뺀다.** 같은 링크를 본문과 하단에 중복하지 않는다.
  - "직접 활용"의 기준: 특정 수치·발언·정의·정책을 그 출처를 들어 본문에서 인용한 경우. 예: "Chroma 연구팀이 ...정량적으로 보였다" -> 그 자리에 인라인 링크.
  - 출처를 들었지만 특정 페이지를 콕 인용하지 않고 포괄적으로만 언급한 경우(예: "공식 문서에 따르면" 수준)는 무리하게 인라인화하지 말고 하단 참고 자료에 둔다. (인라인 링크가 한 문단에 몰리면 가독성을 해친다.)
  - 본문에 인라인 링크가 전혀 없는 보조/심화 자료만 하단 `:::ref`에 남긴다.
- **같은 URL은 글 전체에서 링크를 한 번만 건다.** 같은 출처(특히 내부 글 링크, 예: `[토큰의 원리](/260610)`)를 본문에서 여러 번 언급하더라도 링크는 **첫 등장에만** 걸고, 이후 등장은 링크 없이 텍스트로만 둔다. (문구는 그대로 두되 마크다운 링크 문법만 제거한다.)

### 참고 자료 섹션
- 글 하단의 참고 자료는 `:::ref` 블록으로 작성한다.
- 각 항목은 `[타입] [링크텍스트](url)` 형식으로 작성한다. 타입: `paper`, `docs`, `repo`, `article`
- 링크 텍스트는 **저자나 기관명을 앞에** 두는 방식으로 작성한다. 예: `[article] [TkDodo, React Query Error Handling](url)`
- em dash(—)나 하이픈(-)을 링크 텍스트 안에서 제목과 부제목 구분 용도로 사용하지 않는다. 필요시 공백이나 쉼표로 대체한다.
  - 지양: `[repo] [pmndrs/zustand — 소스코드](url)`
  - 권장: `[repo] [pmndrs/zustand 소스코드](url)` 또는 `[repo] [pmndrs/zustand](url)`
- **하단 참고 자료에는 본문에서 인라인으로 건 링크를 중복해 넣지 않는다.** (위 "링크 사용 규칙" 참고)

### 결론부 패턴
- 글 전체 논지를 1-2문단으로 **압축 요약**
- 독자에게 **말을 건네는 형식**으로 마무리
- 미래에 대한 **겸손한 불확실성** 표현
  - 예: "정답은 없지만... 이 글을 읽는 독자 분들도 각자만의 답을 찾아보기를 바란다."

### 블로그 포스트 프론트매터 형식
```yaml
---
emoji: [적절한 이모지]
title: '[포스트 제목, 짧고 명확하게]'
seoTitle: '[선택: 검색엔진용 긴 제목, 50~60자, 핵심 키워드 포함]'
date: '[YYYY-MM-DD]'
updatedAt: '[선택: 의미 있는 본문 수정일, YYYY-MM-DD]'
categories: [공백으로 구분된 카테고리]
description: '[검색 결과 스니펫용 메타 디스크립션, 120~160자, 핵심 키워드 포함]'
keywords: '[쉼표로 구분된 검색 타겟 키워드 5~8개, 롱테일 키워드 위주]'
---
```

### SEO 작성 가이드
- **title**: 사이트에 표시되는 H1/카드 제목. 짧고 본질적으로. 예: `"추상화"`, `"도메인 모델"`
- **seoTitle** (선택): 짧은 `title`로 사이트 가독성을 지키면서 검색엔진엔 풍부한 키워드를 노출하고 싶을 때 사용.
  - `<title>` 태그, OG, 트위터, JSON-LD `alternativeHeadline`에 모두 반영됨
  - 50~60자 권장 (구글 검색결과에서 잘리지 않는 길이)
  - 메인 키워드 + 보조 키워드 + 액션/혜택 패턴으로 작성. 예: `"프론트엔드 추상화, 좋은 코드를 위한 설계 원칙"`
  - 미지정 시 `title`이 자동 대체되므로, 키워드 강화가 필요한 글에만 추가하면 됨
- **description**: 글의 핵심 내용과 독자가 얻을 가치를 명확히 전달. 주요 검색 키워드를 자연스럽게 포함.
- **keywords**: 구체적이고 검색량이 있는 롱테일 키워드 위주. 한글/영문 혼용 가능.
- **updatedAt** (선택): 오탈자 수정이 아니라 결론, 근거, 예제처럼 독자가 다시 확인할 만한 본문이 바뀌었을 때만 실제 수정일을 기록. 새 글에는 넣지 않으며 Git 커밋 시각으로 자동 생성하지 않음.

### 발행 전 SEO 체크리스트 (필수 점검)

글을 작성/리파인한 뒤, 발행 전에 아래를 반드시 확인한다. (실제 운영 데이터상 `description`/`keywords`가 비면 노출은 되는데 클릭이 0에 수렴하는 사례가 확인됐다. 메타데이터 누락은 곧 트래픽 손실이다.)

- [ ] **description 길이 120~160자**: 한글은 검색결과 스니펫에서 픽셀 폭이 커 160자 이전에 잘릴 수 있으므로 160자를 넘기지 않는다. (초과 시 꼬리가 잘림)
- [ ] **seoTitle 50~60자**: 구글 검색결과 제목이 잘리지 않는 길이. 메인 키워드를 앞쪽에 배치한다.
- [ ] **title과 seoTitle 중복 금지**: title은 사이트 표시용 짧은 제목, seoTitle은 검색용 긴 제목으로 역할을 분리한다.
- [ ] **keywords는 실제 검색 쿼리 기반**: 가능하면 GSC(Google Search Console) 데이터로 실제 유입 쿼리를 확인해 반영한다. (`pnpm gsc` 실행, 아래 "GSC 데이터 활용" 참고)
- [ ] **본문 첫 문단에 핵심 쿼리 자연 배치**: 구글 스니펫이 본문에서 생성되므로, 타겟 쿼리를 첫 문단에 자연스럽게 포함한다.
- [ ] **내부 링크 1개 이상**: 같은 주제(카테고리)의 기존 글로 본문에서 키워드 앵커 링크를 건다. 예: `[queryKey 관리 패턴](/260104)`. 글끼리 본문 상호 링크는 topical authority의 핵심 신호다.
- [ ] **이미지 alt 텍스트**: 모든 본문 이미지에 설명을 담은 alt를 작성한다. (`![설명](src)` 형식. 빌드 시 누락되면 경고가 출력된다.)

### 사람과 AI가 신뢰하기 쉬운 글 체크리스트

- [ ] 직접 겪은 상황, 실측 결과, 재현 가능한 조건처럼 **필자의 1차 근거**가 있는가?
- [ ] 무엇을 선택했는지만이 아니라 대안과 제약, **그 판단의 이유**를 설명했는가?
- [ ] 독자가 검증할 수 있도록 버전, 환경, 입력값, 실행 절차 등 **재현 조건**을 남겼는가?
- [ ] 핵심 주장은 공식 문서, 표준, 원 논문처럼 가능한 한 **1차 출처**로 연결했는가?
- [ ] AI가 조사·요약·번역을 도왔다면 인용, 수치, 코드와 결론을 사람이 원문과 실행 결과로 다시 확인했는가?

TL;DR, FAQ, 비교표, 고정된 소제목은 필수 형식이 아니다. 독자의 탐색이나 비교를 실제로 돕는 글에서만 선택적으로 사용하고, 모든 글을 같은 템플릿에 맞추지 않는다.

### 비공개(임시 저장) 처리

- 작성 중인 미완성 글은 프론트매터 `categories`에 **`ignore`** 를 넣는다. (예: `categories: ignore`)
- `ignore`가 포함되면 sitemap, RSS, 글 목록, 검색, 개별 페이지(404 처리), llms.txt에서 **완전히 제외**되고 `noindex`가 적용된다. (`src/lib/filter-posts.ts`의 `isHiddenPost`가 판별)
- 발행 시 `ignore`를 제거하고 실제 카테고리로 교체한다.

### GSC 데이터 활용 (실제 검색 성과 기반 글쓰기)

- `pnpm gsc`로 최근 28일 vs 직전 28일 검색 데이터를 수집한다. (`.gsc-data/`에 CSV 4종 저장 + Quick Win/Cannibalization 자동 분류 출력)
- 사전 준비: `.env.local`에 `GOOGLE_SERVICE_ACCOUNT_EMAIL`, `GOOGLE_PRIVATE_KEY`, `GSC_SITE_URL` 설정 + 해당 서비스 계정을 GSC 속성에 사용자로 추가. (GA4와 동일한 서비스 계정 재사용)
- **Quick Win**: position 5~20 + 노출 높음 + CTR 낮은 쿼리 → 해당 글의 seoTitle/description/첫 문단을 그 쿼리에 맞게 개선하면 즉시 효과.
- 글의 keywords는 추측이 아니라 GSC에서 실제로 노출되는 쿼리를 우선 반영한다.
