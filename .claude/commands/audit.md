리포를 여러 관점에서 점검하고, 확인된 문제를 같은 세션에서 고친다.

기계로 확인되는 것은 `pnpm audit:repo` 가 이미 한다. 이 명령어는 그 위에서 판단이 필요한 것만 본다.
보고서로 끝내지 않는다. 확인된 문제는 고치고, 고치지 않은 것은 이유를 밝힌다.

## 0. 먼저 기계 게이트를 직렬로 돌린다

```bash
pnpm audit:repo --build --live
```

결과는 `.audit-report.json` 에 남는다. FAIL 이 있으면 그것부터 처리한다.

**여기서 순서가 중요하다.** `pnpm build` 와 `pnpm rebuild` 는 `.contentlayer` 와 `.next` 를 지운다.
에이전트를 병렬로 띄운 상태에서 누가 빌드를 돌리면 서로의 산출물을 덮어써서,
레포의 문제가 아니라 경쟁 상태의 흔적을 발견하게 된다.
그래서 빌드는 병렬 진입 전에 혼자 한 번만 돌리고, 이후 레인에는 로그 경로를 넘긴다.

## 1. 레인을 병렬로 띄운다

`Agent` 도구로 아래 5개를 **한 응답 안에서** 띄운다. 그래야 동시에 돈다.
각 레인 프롬프트에 다음 세 가지를 반드시 넣는다.

- 읽기 전용이다. `pnpm build`, `pnpm dev`, `pnpm rebuild`, `pnpm content:sync` 금지.
  이유(동시 빌드가 서로를 깨뜨린다)까지 적는다.
- 파일을 고치지 않는다. 수정은 조율하는 쪽이 모아서 한다.
- 먼저 리포 루트 `CLAUDE.md` 를 읽는다. 거기 적힌 의도된 결정을 버그로 보고하지 않게 한다.
  (예: IndexNow 가 카테고리 페이지를 일부러 제출하지 않는 것, Sentry 가 서버 전용인 것)

| 레인 | 무엇을 본다 |
|---|---|
| 기능/동작 | `src/app/**` 라우트 목록과 `[lang]` 미러의 비대칭, `isHiddenPost` 를 적용하지 않는 소비자, `/api/search` 의 입력 검증과 에러 경로, `post-navigation.ts` 와 `localized-posts.ts` 의 경계 조건 |
| SEO | 프로덕션 HTML 을 `curl` 로 직접 본다. sitemap, robots, hreflang 상호성과 `x-default`, 카테고리 `noindex` 판정, JSON-LD 파싱, 전 글 × 6 로케일의 `description`(120~160자) `keywords`(5~8개) 충족, 끊긴 내부 링크. `docs/hreflang-baseline-*.md` 와 대조해 회귀를 찾는다 |
| 관측 | Sentry MCP 로 `hooninedev/jihoon-blog` 미해결 이슈를 조회한다(도구가 deferred 이므로 `ToolSearch` 로 먼저 로드). Sentry 로 보고하지 않고 fallback 만 돌려주는 경로가 어디인지. 명시적 보고 지점은 `src/lib/og-font.ts` 하나이고 나머지는 `onRequestError` 자동 훅이 받는다 |
| 성능 | 0단계 빌드 로그를 읽는다. client JS gzip 합계와 예산, 소스맵 잔존, 라우트 수와 빌드 시간, `curl -I` 로 프로덕션 TTFB 와 캐시 헤더 |
| 콘텐츠 | 번역 검증기가 **무엇을 안 보는지**. 로케일 파일의 한글 비율로 미번역 스텁을 찾고, 로케일별 `description`/`keywords` 누락, 인용 블록 개수 상한(3~5), 같은 URL 중복 링크, 본문 인라인 링크와 `:::ref` 중복 |

각 레인에 요구할 출력 형식은 같다. 항목마다 `file:line` 또는 URL, 무엇이 틀렸는지,
**구체적인 실패 시나리오(입력에서 잘못된 출력까지)**, 심각도, 그리고 직접 코드 경로를 끝까지 읽은
CONFIRMED 인지 SUSPECTED 인지. 스타일 지적으로 목록을 채우지 말라고 명시한다.

## 2. 보고를 검증한 뒤에 고친다

에이전트 보고를 그대로 믿지 않는다. 고치기 전에 각 항목을 직접 확인한다.

- 오탐이 가장 많이 나오는 자리는 세 곳이다. 오래된 글의 이미지는 `content/` 가 아니라
  `public/content/` 에 있다. 코드 블록 안의 em dash 는 번역본 5개가 바이트 단위로 같아야 하므로 손대지 않는다.
  영어·스페인어·포르투갈어 번역본의 em dash 는 그 언어의 정상 구두점이다.
- 한글 원문(`index.md`)을 한 글자라도 고치면 그 글의 번역본 5개가 전부 stale 이 된다.
  프론트매터 포함 파일 전체가 해시 대상이다. 고칠 값어치가 있는지 먼저 따진다.
  고치기로 했으면 `CLAUDE.md` 의 「다국어 번역」 절차를 그대로 따르고 `pnpm content:translations` 로 닫는다.

수정 후에는 `pnpm audit:repo --build` 를 다시 돌려 회귀가 없는지 확인한다.

## 3. 남기는 것

- 고친 것: 무엇을 왜 고쳤는지 커밋 메시지에.
- 안 고친 것: 왜 안 고쳤는지 답변에 명시한다. "남았다"고만 적고 넘기지 않는다.
- 예산이 바뀌었으면 `scripts/audit.mjs` 의 `BUDGET` 과 `CLAUDE.md` 의 실측 수치를 같이 갱신한다.
  문서의 수치가 실측과 어긋난 채로 남으면 다음 번에 회귀를 판정할 기준이 사라진다.

## 문체

전역 지침대로 `—`(em dash)와 `–`(en dash)를 문장 부호로 쓰지 않는다.
답변, 커밋 메시지, 코드 주석, 새로 쓰는 문서 전부에 적용된다.
