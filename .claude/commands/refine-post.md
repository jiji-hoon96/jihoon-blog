이미 작성된 블로그 글을 jihoon 스타일로 리파인해주세요.

## 작업 순서

1. 대상 파일을 읽습니다.
2. 현재 글의 **구조, 톤, 표현**을 분석합니다.
3. 글에 포함된 기술적 내용의 **사실 관계와 최신성을 검증**하기 위해 웹 검색으로 리서치합니다.
4. 아래 체크리스트에 따라 개선점을 파악하고, 리서치 결과를 반영하여 수정합니다.
5. 수정된 글을 원본 파일에 반영합니다.

## 리파인 체크리스트

### 구조
- [ ] 도입부에 "이번 포스팅에서는 [주제]에 대한 이야기를 해보려고 한다." 패턴이 있는가?
- [ ] 도입부에서 개인적 경험이나 동기가 2-3문단에 걸쳐 설명되는가?
- [ ] 글 전체의 핵심 주장과 절별 독자 획득점을 각각 한 문장으로 정리했는가? 이 메모는 공개 원고에 자동으로 넣지 않는다.
- [ ] H2와 H3만 따로 읽어도 문제 제기, 설명, 판단의 흐름이 드러나는가?
- [ ] 각 소제목이 해당 절의 핵심 개념을 **명사구로** 대표하는가? 명사구로 안 될 때만 짧은 문장을 썼는가?
- [ ] 소제목이 **20자를 넘는 것**이 몇 개인가? 25자를 넘으면 두 가지를 한 제목에 넣은 것이 아닌지 본다
  - API 이름이나 식별자 하나가 길어서 생긴 길이는 세지 않는다. 식별자를 뺀 나머지로 잰다
  - 길이보다 먼저 보는 것은 그 제목이 절의 **개념**인지 절의 **판정**인지다
- [ ] 서술형 종결(`~한다`, `~않는다`)로 끝나는 소제목이 **절반을 넘지 않는가?** 판정문이 계속 이어지면 어느 것이 결론인지 흐려진다
- [ ] 질문형을 소제목이 아니라 절 전환 문장에 썼는가?
- [ ] **마지막 H2 가 앞의 H2 들을 결정 하나로 묶는가?** 묶이지 않으면 논증이 아니라 카탈로그다. 절을 합치거나 마지막 절에서 결정을 명시한다
- [ ] 어떤 H2 를 빼도 마지막 결정이 그대로 서는 절이 있는가? 있다면 그 절은 논지에 기여하지 않는다
- [ ] 한 소제목에 여러 주제를 묶거나 본문보다 넓고 추상적인 표현을 쓰지 않았는가?
- [ ] 소제목과 첫 문단이 같은 내용을 반복하지 않고 서로 보완하는가?
- [ ] 섹션 전환이 질문을 통해 자연스럽게 이루어지는가?
- [ ] 결론부가 논지를 압축 요약하고 독자에게 말을 건네는가?
- [ ] 글 전체의 문맥 흐름이 자연스러운가? 독자가 읽다가 흐름이 끊기거나 어색한 지점이 없는가?

### 위에서 아래로 읽는 논지 검증

먼저 실제 원고에서 핵심 질문, 핵심 답, 포함 범위, 제외 범위를 각각 한 문장으로 추출한다. 저자가 의도했을 것 같은 주제가 아니라 현재 원고가 실제로 말하는 내용을 적는다.

그다음 모든 문단을 다음 형식으로 reverse outline 한다. 이 표는 편집 메모이며 공개 원고에 자동으로 넣지 않는다.

| 위치 | 한 줄 요지 | 문단의 역할 | 앞 문단과의 관계 | 핵심 답과의 관계 | 조치 |
|---|---|---|---|---|---|

조치는 `유지`, `이동`, `분리`, `통합`, `연결 보강`, `삭제` 중 하나를 사용한다.

- [ ] 각 문단에서 중심 요지를 하나만 추출할 수 있는가?
- [ ] 각 문단이 정의, 주장, 근거, 예시, 해석, 반론, 전환, 결론 중 어떤 역할을 하는지 설명할 수 있는가?
- [ ] 문단의 첫 문장이 실제 중심 내용을 알리고, 뒤 문장이 그 내용을 진전시키는가?
- [ ] 모든 문단이 핵심 답을 설명하거나 검증하는 데 기여하는가? 관련은 있지만 기여하지 않는 내용은 이동하거나 삭제했는가?
- [ ] 개념의 정의와 전제가 처음 사용되기 전에 나오는가?
- [ ] 앞 문단의 결론이 다음 문단을 읽어야 할 이유를 만드는가? 단순한 접속사로 논리적 간격을 가리고 있지 않은가?
- [ ] 같은 주장과 배경 설명이 도입, 본문, 결론에서 필요 이상으로 반복되지 않는가?
- [ ] 절의 첫 문단이 다룰 질문이나 중심 내용을 좁히고, 마지막 문단이 답 또는 다음 절로 넘어갈 근거를 남기는가?
- [ ] 질문형 전환이 실제 독자의 질문을 반영하는가? 문맥 없이 반복되는 수사적 질문은 평서문이나 구체적인 한계로 바꿨는가?
- [ ] 제목, 도입, H2와 H3만 읽었을 때 글의 주제와 범위가 보이는가?
- [ ] 각 문단의 첫 문장만 위에서 아래로 읽었을 때 주장이 누적되고 결론에 도달하는가?
- [ ] 처음 읽는 독자가 뒤에서 나올 정보를 미리 알아야 이해할 수 있는 문단이 없는가?

시리즈 글에는 다음 항목도 적용한다.

- [ ] 각 글이 답하는 핵심 질문이 서로 구분되는가?
- [ ] 앞 글의 내용을 다시 설명할 때 현재 글에 필요한 만큼만 압축했는가?
- [ ] 다음 글의 핵심 내용을 미리 해결하지 않고, 현재 글의 결론에서 다음 질문만 넘겨주는가?

흐름 문제를 `어색하다`라고만 기록하지 않는다. `어떤 문단에서`, `독자가 무엇을 아직 모르는 상태이며`, `어떤 논리 단계가 빠졌거나 반복됐는지`, `이동·분리·삭제·연결 중 무엇을 할지`까지 적는다.

### 네 가지 독자 관점

1. 입문자: 사전 지식, 첫 용어 설명, 지시어, 생략된 주어, 문장당 새 개념 수를 확인한다.
2. 실무자: 계측 지점, 선택 기준, 제약, 실패 사례와 운영 비용을 확인한다.
3. 전문가: 전제, 근거, 적용 범위, 예외, 반례와 대안을 확인한다.
4. 회의적 독자: 사실, 추론, 의견이 구분되는지와 가장 강한 반론에 답하는지 확인한다.

각 지적은 대상 문단, 예상되는 오해, 수정 방향을 함께 적는다. "어렵다", "더 명확하게"처럼 수정 위치와 이유가 없는 평가는 사용하지 않는다.

  - 권장: "Stanford 연구팀(Liu et al.)은...", "React 코어팀의 Andrew Clark은..."

### 마크다운 문법
- [ ] 강조에 `**텍스트**` (볼드)만 사용했는가? `*텍스트*` (이탤릭)가 남아있다면 볼드로 바꾸거나 괄호 코멘트로 풀어준다.
- [ ] em dash(—)나 하이픈(-)을 문장 이음, 설명 연결, 제목·부제 구분 용도로 사용하지 않았는가? (본문·소제목·목록·프론트매터 seoTitle·`:::ref` 링크 텍스트 모두 포함. **외부 원문 인용 블록은 예외이며 원문 구두점을 그대로 둔다**)
  - 지양: `방향 1 — harness`, `2025년 10월 — Agent Skills`, `Zustand — 소스코드`, `상태를 구독하고 — 변경을 감지한다`
  - 권장: 쉼표, 콜론(`:`), 마침표, 또는 자연스러운 문장 구조로 대체

### 괄호 사용 (작업 흔적이 가장 잘 남는 자리)
- [ ] 괄호 안에 **작업 과정의 흔적**이 남아 있지 않은가? `(이 세션의 요청에 없었던 것이다)`, `(다시 빌드해 보지 않아 모른다)`, `(필자는 실측 전에 알았어야 했다)` 같은 문장이다
  - 독자는 이 글이 어떤 절차로 쓰였는지 모르고 알 필요도 없다
  - **남길 값어치가 있는 한계라면 괄호가 아니라 본문 문장으로 올린다.** 그 자리에서 논지의 일부가 된다
- [ ] **60자를 넘는 괄호**를 전부 찾아 하나씩 검토했는가? 길이는 괄호 안쪽 글자 수로 세고 공백을 포함한다
  - 60자 초과가 곧 잘못은 아니다. 검토 신호이고, 걷어낼 것은 작업 흔적과 완결된 문장 두 개 이상이다
- [ ] 괄호 안에서 주장을 펴고 근거를 대고 있지 않은가? 완결된 문장이 두 개 이상이면 그것은 보충이 아니라 문단이다
- [ ] 같은 형태의 **계산식 괄호**가 세 번 넘게 반복되지 않는가? (`(68 - 50)`, `(66 - 50)` 같은 것) 반복되면 표로 옮긴다
- [ ] **그림 출처와 라이선스가 본문 괄호에 들어가 있지 않은가?** 표기 자체는 재사용 조건이라 지우면 안 되고, 그림 아래 독립된 줄로 내린다
- [ ] 남은 괄호가 전부 **독자에게 보여줄 내용**인가? 영어 원어 병기, 한 문장 보충, 필자의 소견 셋 중 하나여야 한다

### 인용 밀도 (리파인에서 가장 먼저 볼 것)
- [ ] 인용 블록(`> `)이 **3~5개 이하**인가? (250줄 안팎의 글에서 10개가 넘으면 과하다)
- [ ] 남은 인용이 전부 **필자의 논지를 뒷받침**하는가? 출처가 존재한다는 것만 증명하는 인용은 없는가?
- [ ] 인용 블록 사이에 필자의 문단이 최소 하나 들어가 있는가? (인용 블록이 곧바로 이어지지 않아야 한다)
- [ ] 걷어낼 때 **인라인 링크는 남기고 인용 블록만 지우고 내용을 필자의 문장으로 옮겼는가?** (근거 추적성은 링크가 담당한다)
- [ ] 인용을 걷어낸 자리를 필자의 해석과 경험으로 채웠는가? (단순 삭제로 끝내면 글이 얇아진다)

### 시각 자료
- [ ] `그림이나자료필요` 플레이스홀더가 남아 있지 않은가? (이 문법은 렌더링되지 않고 프롬프트가 본문에 그대로 노출된다. 발견하면 **이미지를 만들어 교체**하거나 문장으로 대체한다)
- [ ] 본문의 모든 `![](N.png)` 참조에 대해 **실제 파일이 `content/YYMMDD/`에 존재**하는가?
- [ ] alt 텍스트가 그림의 내용을 설명하는 문장인가? (`![1.png](1.png)` 형태로 방치되지 않았는가)
- [ ] 폭 지정(`?w=`)이 도표 성격에 맞는가? (넓은 도표 720, 좁은 도표 500 기준. 그 사이 값도 허용된다)
- [ ] 도표 하단 해설이 본문 인접 문단의 재진술은 아닌가? (같은 말이면 해설을 지우거나 본문에 없는 관찰로 교체한다)
- [ ] 도표가 뒤 절의 반전이나 결론을 미리 흘리고 있지 않은가?
- [ ] 구조나 수치 대비를 텍스트만으로 설명하는 지점이 남아 있다면, 도표로 만들 수 있는지 검토했는가? (제작 방법은 `write-post.md`의 시각 자료 가이드 참고)
- [ ] **이해가 막히는 지점에 그림이 있는가?** 텍스트로 두 문단이 걸리는 구조, 시간 순서, 포함 관계, 경계선이 그림 없이 설명되고 있지 않은가
  - 이 자리에서 독자가 얻는 것이 가장 크다. 숫자는 문장으로도 전달되지만 구조는 잘 안 된다
  - 시각적 기준은 `content/260914/2.png` 다. INP 를 세 구간으로 나눠 시간축에 놓았고, 같은 내용을 문장으로 쓰면 한 문단이 걸린다. (그 파일은 web.dev 원본이므로 우선순위 2번 사례다)
- [ ] **숫자 몇 개를 카드에 담아 늘어놓은 그림이 있지 않은가?** 값 세 개를 보여주려고 대시보드 모양을 만들었다면 그 자리는 문장이나 표가 낫다
  - 물어볼 것: 이 그림이 없으면 독자가 무엇을 놓치는가. 답이 "숫자를 빨리 본다" 뿐이면 표로 바꾼다
- [ ] 개념을 설명하는 그림을 **다크 테마 카드 레이아웃으로** 만들지 않았는가? 그 형식은 수치용이고, 구조를 담으면 대시보드 스크린샷처럼 보인다
- [ ] 출처에 쓸 만한 그림이 있는데 직접 그리지 않았는가? 공식 문서나 명세의 그림이 라이선스를 허락하면 원본이 낫다

- [ ] "어려웠다", "복잡하다" 같은 서술이 **확인 가능한 구체적 장벽**으로 내려와 있는가?
- [ ] 과거의 작업을 다루는 글이라면 **현재 상태를 다시 조회**했는가? (고쳤다고 쓴 것이 지금도 고쳐진 상태인지)
- [ ] 필자의 실제 배경(회사에서의 Sentry 경험, 개인 블로그의 Google Analytics/Search Console 운영)과 어긋나는 초심자 프레이밍이 없는가?
- [ ] **성능이나 개선을 주장하는 수치마다 측정 조건이 붙어 있는가?** 장비, 버전, 도구, 반복 횟수, 조회 시점 중 해당하는 것을 적었는지 본다
  - 이 항목은 규칙이 있는지가 아니라 **매번 지켜지는지**를 본다. D2 는 2011년과 2017년 글에서 장비 제원과 "10회 반복해서 측정한 값의 중간값" 까지 밝혔는데, 368편 전수에서 성능을 언급한 238편 중 조건 세 범주 이상을 밝힌 글은 10편(4%)이었다
  - 규칙은 저절로 유지되지 않는다. 같은 블로그에서 번호 캡션이 2017년 278건에서 2024년 0건이 됐고 참고 자료 절도 사라졌다
- [ ] 조건이 붙은 작은 숫자가 있는가? 규모가 큰 숫자보다 **재현 조건이 붙은 작은 숫자**가 설득력이 크다

### 사실 관계 및 최신성
- [ ] 리서치는 현재 시점(프롬프팅 시점) 기준으로 수행했는가? 글이 과거에 작성되었더라도 현재 최신 버전과 생태계 현황을 반영해야 한다.
- [ ] 기술적 주장(성능 수치, 동작 원리, 비교 등)이 정확한가?
- [ ] 버전, 생태계 현황 등이 현재 시점 기준으로 최신인가?
- [ ] 리서치를 통해 보강할 수 있는 내용(최신 동향, 대안, 사례)이 반영되었는가?
- [ ] 기술 용어의 정의와 약어 풀이가 정확한가?
- [ ] **헤지로 덮은 오류가 없는가?** 앞에서 단정한 사실이 뒤에서 이상해졌을 때, 괄호로 인정만 하고 앞 문장을 고치지 않은 자리를 찾는다
  - 실제 사례가 있다. 어떤 글이 "SOP는 2011년 RFC 6454에서 처음 등장한 보안 정책" 이라고 쓴 뒤, 다음 문단에서 "(참고로 CORS라는 이름이 처음 등장한 것은 2009년이라, SOP의 등장보다 빠르다)" 로 시간선이 이상함을 인정했다. 그런데 전제를 재검토하지 않았다. RFC 6454 원문은 "Traditionally, user agents have divided content according to its origin" 이라고 쓴다
  - **모르는 것을 드러내는 것과 틀린 것을 고치는 것은 다르다.** 이상하다고 느꼈으면 그 자리에서 원문을 다시 확인하고 앞 문장을 고친다
- [ ] "~인 것 같다", "~로 보인다" 가 **실제 불확실성**인가, 확인을 미룬 자리인가? 후자면 확인하고 단정한다

### SEO
- [ ] `title`이 짧고 명확한가? (사이트 H1/카드에 표시되므로 깔끔하게)
- [ ] 검색 노출을 강화하고 싶은 글이라면 `seoTitle` (50~60자, 핵심 키워드 포함)을 추가했는가?
  - `seoTitle`은 `<title>` 태그, OG, 트위터, JSON-LD `alternativeHeadline`에 반영됨

  - 예: title `"추상화"` + seoTitle `"프론트엔드 추상화, 좋은 코드를 위한 설계 원칙"`

- [ ] 프론트매터에 `keywords` (구체적 롱테일 키워드 5~8개)가 있는가?
