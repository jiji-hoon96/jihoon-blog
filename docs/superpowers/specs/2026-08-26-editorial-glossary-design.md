# 글쓰기 검증과 용어 해설 시스템 설계

작성일: 2026-08-26

## 요약

이 설계는 블로그 글을 더 빠르게 탐색하고, 서로 다른 배경의 독자가 같은 글을 무리 없이 이해하도록 돕는다. 작업은 두 축으로 나뉜다.

1. 목차 제목과 원고 검토 방식을 글쓰기 가이드에 명문화한다.
2. 작성자가 명시한 전문 용어를 중앙 다국어 용어집과 연결하고, 데스크톱에서는 말풍선으로, 터치 환경에서는 하단 패널로 설명한다.

첫 적용 대상은 `docs/research/observability-series/260703.md`, `260704.md`, `260705.md`의 한국어 초안이다. 한국어 원고가 승인되기 전에는 운영 중인 `content/260703/index.md`와 번역 파일을 교체하지 않는다.

## 목표

- 목차만 읽어도 각 절의 주제와 글의 논리 흐름을 파악할 수 있게 한다.
- 입문자, 실무자, 전문가, 회의적 독자의 관점에서 원고를 검토하는 반복 가능한 절차를 만든다.
- 어려운 용어를 본문 흐름을 끊지 않는 짧은 해설과 연결한다.
- 마우스, 키보드, 터치 환경에서 같은 정보를 접근 가능하게 제공한다.
- 용어 정의를 한곳에서 관리하고 번역 누락과 잘못된 키를 검증한다.

## 범위에서 제외하는 것

- 기존 게시물 전체의 용어를 자동으로 탐지하거나 일괄 변환하지 않는다.
- 첫 버전의 용어 설명에는 Markdown, HTML, 이미지, 중첩 링크를 허용하지 않는다.
- 모바일 하단 패널에 드래그 제스처를 추가하지 않는다.
- 용어 클릭 분석이나 별도 검색 색인을 추가하지 않는다.
- AI가 원고를 자동 승인하거나 의미 품질을 점수화하지 않는다.

## 결정한 접근법

### 명시적 용어 표기와 중앙 용어집

작성자가 설명이 필요한 위치를 직접 표시한다.

```md
:term[RUM]{key="rum"}
```

자동 탐지는 일반 단어와 전문 용어의 경계를 안정적으로 판단하기 어렵고 표시가 과해질 수 있어 제외한다. 설명을 글마다 인라인으로 작성하는 방식은 중복과 번역 비용이 커서 제외한다.

용어 표기는 다음 원칙을 따른다.

- 독자가 해당 절을 이해하는 데 필요한 용어만 표시한다.
- 같은 절에서는 첫 번째 의미 있는 등장에 표시하는 것을 기본으로 한다.
- 긴 글에서 문맥이 충분히 끊긴 경우에만 같은 용어를 다시 표시한다.
- 용어 해설은 본문 설명을 대체하지 않는다. 핵심 논리 자체가 용어 해설에만 존재해서는 안 된다.

### 기기에 맞춘 해설 UI

- 정밀 포인터와 hover를 지원하는 환경에서는 용어 가까이에 말풍선을 표시한다.
- 터치 또는 거친 포인터 환경에서는 화면 아래의 해설 패널을 표시한다.
- 화면 너비만으로 기기를 구분하지 않고 `hover`와 `pointer` 미디어 기능을 우선한다.
- 키보드 focus는 화면 크기와 관계없이 접근 가능한 해설을 제공한다.

## 편집 가이드 설계

### 목차 제목

H2와 H3 제목은 본문을 압축한 문장이 아니라 해당 절을 찾기 위한 탐색 표지다.

- 절의 핵심 개념, 질문 또는 주장을 짧은 명사구나 짧은 문장으로 표현한다.
- 제목만 순서대로 읽어도 글의 논리 전개가 드러나야 한다.
- 하나의 제목에 여러 주제를 쉼표나 접속사로 묶지 않는다.
- 추상적인 비유보다 본문에서 실제로 설명하는 단어를 우선한다.
- 글자 수를 기계적으로 제한하지 않되 모바일 목차에서 한눈에 읽히는 길이를 우선한다.
- 제목과 첫 문단이 같은 문장을 반복하지 않고 서로 보완하게 한다.

원고 검토 시 H2와 H3만 따로 추출해 다음을 확인한다.

1. 서로 다른 절을 구분할 수 있는가.
2. 제목 순서만으로 문제 제기, 설명, 판단의 흐름이 보이는가.
3. 제목이 실제 본문 내용보다 넓거나 좁지 않은가.
4. 동일한 추상어가 반복되어 탐색성이 떨어지지 않는가.

### 네 가지 독자 관점

원고를 다듬기 전에 글 전체의 핵심 주장을 한 문장으로 정리하고, 각 절에서 독자가 얻어야 할 내용을 한 문장으로 적는다. 그다음 아래 관점을 순서대로 적용한다.

핵심 주장, 절별 독자 획득점과 관점별 검토 메모는 편집 과정의 산출물이다. 작성자가 본문에 포함하기로 판단한 내용만 게시물에 남기고, 검토 메모 자체를 공개 원고에 자동 삽입하지 않는다.

#### 입문자

- 필요한 사전 지식이 설명되거나 연결되어 있는가.
- 추상적인 설명 전에 구체적인 상황이나 예시가 있는가.
- 지시어, 생략된 주어, 긴 수식어 때문에 문장을 다시 읽어야 하지 않는가.
- 새로운 전문 용어가 한 문단에 몰리지 않는가.

#### 실무자

- 관찰 지점, 선택 기준, 제약 조건이 실제 업무에 적용 가능한가.
- 정상 경로뿐 아니라 실패 사례와 운영상의 비용을 다루는가.
- 도구 이름을 나열하는 데 그치지 않고 언제 무엇을 판단할 수 있는지 설명하는가.

#### 전문가

- 주장의 범위, 전제, 근거와 한계가 명확한가.
- 일반화하기 어려운 사례를 보편적인 결론처럼 표현하지 않는가.
- 반례나 대안이 결론을 바꾸는 조건을 설명하는가.

#### 회의적 독자

- 확인된 사실, 근거에 기반한 해석, 저자의 의견을 구분할 수 있는가.
- 가장 강한 반론을 회피하지 않고 답하는가.
- 제품이나 도구를 과장하지 않고 관측할 수 없는 영역도 밝히는가.

검토 결과는 `어렵다`처럼 추상적인 평가로 끝내지 않는다. 문제가 있는 문단, 독자에게 생기는 오해, 수정 방향을 함께 기록한다.

### 가이드 반영 위치

- `CLAUDE.md`: 프로젝트 전체에 적용되는 짧은 원칙과 필수 검증 항목
- `.claude/commands/write-post.md`: 목차 설계, 핵심 주장, 절별 독자 획득점, 용어 표기 절차
- `.claude/commands/refine-post.md`: 네 독자 관점의 순차 검토와 수정 결과 형식
- `docs/translation-review.md`: `term` 키 보존, 표시 이름의 자연스러운 번역, 언어별 용어 정의 검증

## 용어 데이터 모델

중앙 용어집은 `content/glossary.json`에 둔다. 각 키는 안정적인 소문자 kebab-case 식별자이며, 언어별로 이름과 짧은 정의를 가진다.

```json
{
  "rum": {
    "ko": {
      "name": "RUM",
      "definition": "실제 사용자의 환경에서 성능과 경험 데이터를 수집하는 방식"
    },
    "en": {
      "name": "RUM",
      "definition": "A way to collect performance and experience data from real user environments"
    }
  }
}
```

정의는 평문 한두 문장으로 제한한다. 첫 버전에는 링크나 임의 HTML 필드를 두지 않는다. Markdown에 적힌 표시 문자열은 문장에 자연스럽게 어울리는 표현이고, 용어집의 `name`은 말풍선 또는 하단 패널의 제목이다.

모든 용어가 모든 언어를 즉시 가질 필요는 없다. 다만 특정 언어의 게시물에서 참조된 키는 해당 언어의 `name`과 `definition`을 반드시 가져야 한다.

## Markdown 변환과 데이터 흐름

### 변환 단계

새 `remark-term` 플러그인이 `textDirective` 중 이름이 `term`인 노드를 처리한다.

- 표시 문자열과 `key`를 읽는다.
- 문법이 올바르면 평문 표시 문자열과 `data-glossary-key`를 가진 점진적 향상용 요소를 출력한다.
- JavaScript가 실행되지 않아도 본문은 일반 텍스트처럼 읽혀야 한다.
- 알 수 없는 속성이나 임의 HTML은 출력하지 않는다.

플러그인은 `contentlayer.config.ts`의 기존 `remarkDirective` 뒤에 등록한다.

### 런타임 단계

게시물 본문에는 고정된 용어 루트 식별자를 부여한다. `GlossaryTerms` 클라이언트 컴포넌트는 현재 언어에 필요한 용어 데이터만 전달받아 다음을 수행한다.

1. 루트 안의 `data-glossary-key` 요소를 찾는다.
2. 현재 언어의 정의가 있는 요소만 실제 인라인 버튼으로 향상한다.
3. 이벤트 위임으로 hover, focus, 클릭과 터치 입력을 처리한다. `pointerdown`의 `pointerType`과 최근 키보드 입력을 기록해 터치로 생긴 focus와 키보드 focus를 구분한다.
4. 하나의 공유 말풍선 또는 하나의 공유 하단 패널만 렌더링한다.
5. 닫힐 때 터치로 열었던 용어로 focus를 돌려준다.

공유 UI를 사용해 용어마다 React 트리를 만들지 않는다. 게시물당 열린 용어는 최대 하나다.

`src/lib/glossary.ts`가 JSON 스키마 검증과 언어별 데이터 선택을 담당한다. 서버 페이지는 현재 언어의 항목만 `GlossaryTerms`에 전달해 다른 언어의 정의를 클라이언트 번들에 포함하지 않는다. `src/lib/glossary-ui.ts`에는 입력 방식 판별, 열림 상태 전이와 말풍선 위치 계산처럼 DOM에서 분리해 테스트할 수 있는 순수 로직을 둔다.

## 상호작용과 접근성

### 마우스와 키보드

- 정밀 포인터의 hover 또는 키보드로 이동한 focus 시 용어 가까이에 말풍선을 연다.
- 클릭하면 말풍선을 고정하거나 닫는다.
- focus가 다른 곳으로 이동하거나 포인터가 용어와 말풍선 영역을 벗어나면 고정되지 않은 말풍선을 닫는다.
- `Escape`와 바깥 클릭은 열린 말풍선을 닫는다.
- 말풍선은 화면 경계를 넘으면 위아래 또는 좌우 위치를 조정한다.

### 터치

- 용어를 누르면 하단 해설 패널과 배경 가림막을 연다.
- 가림막, 닫기 버튼 또는 `Escape`로 닫는다.
- 패널이 열리면 배경 스크롤을 잠그고, 닫히면 원래 상태로 복구한다.
- 패널이 열리면 닫기 버튼으로 focus를 이동하고, 열린 동안 focus를 패널 안에 유지하며, 닫을 때 원래 용어로 돌려준다.
- 첫 버전에는 스와이프나 드래그 닫기를 구현하지 않는다.

### 의미 구조

- 향상된 용어는 네이티브 `button`을 사용한다.
- 열린 상태는 `aria-expanded`와 `aria-controls`로 연결한다.
- 데스크톱 해설은 `role="tooltip"`을 사용하고 열린 동안 `aria-describedby`로 용어와 연결한다.
- 모바일 하단 패널은 제목이 있는 `role="dialog"`와 `aria-modal="true"`를 사용하며 용어 버튼에 `aria-haspopup="dialog"`를 둔다.
- 키보드 focus 윤곽을 제거하지 않는다.
- 용어는 점선 밑줄로 구분하고, 열린 상태에만 배경 강조를 적용한다.

## 오류 처리와 안전성

- 잘못된 directive 문법, 존재하지 않는 키, 참조 언어의 정의 누락은 콘텐츠 검증 명령이 파일과 위치를 포함해 보고한다.
- 런타임에서 키나 정의를 찾지 못하면 해당 요소는 버튼으로 향상하지 않고 일반 텍스트로 남긴다.
- 용어 이름과 정의는 텍스트로만 렌더링하며 `dangerouslySetInnerHTML`을 사용하지 않는다.
- 한 용어의 오류가 게시물 렌더링 전체를 막지 않는다.
- 개발 환경에서는 누락을 경고하되 운영 사용자에게 내부 오류 메시지를 노출하지 않는다.

## 초기 콘텐츠 적용

한국어 초안 세 편에 다음 순서로 적용한다.

1. 각 글의 핵심 주장과 절별 독자 획득점을 정리한다.
2. H2와 H3만 읽어 흐름을 검토하고 짧은 탐색 표지로 수정한다.
3. 네 독자 관점에서 난해한 문장, 근거 부족, 과도한 일반화를 수정한다.
4. 글을 이해하는 데 반드시 필요한 전문 용어의 첫 의미 있는 등장만 표시한다.
5. 필요한 한국어 용어 정의를 중앙 용어집에 추가한다.

초기 적용은 연구 초안에만 수행한다. 운영 게시물과 번역 콘텐츠로 옮기는 작업은 한국어 원고 검토가 끝난 뒤 별도 단계로 진행한다.

## 검증 전략

### 자동 검증

기존 테스트 방식을 따라 Node 기반 테스트를 우선한다.

- 올바른 `term` directive가 예상한 점진적 향상 요소로 변환되는지
- 표시 문자열과 키가 안전하게 이스케이프되는지
- 문법 오류, 존재하지 않는 키와 언어별 정의 누락을 파일 위치와 함께 찾는지
- 상호작용 상태가 열기, 고정, 입력 방식 전환, 닫기를 예측 가능하게 처리하는지
- 말풍선 위치 계산이 화면 경계를 벗어나지 않는지
- 용어집 JSON의 키와 언어별 필드가 스키마를 만족하는지

`content:glossary` 명령은 기본적으로 `content/**/*.md`를 검사하고, `--drafts` 옵션을 주면 초기 연구 초안 세 편도 함께 검사한다. `build`는 기본 명령을 Contentlayer 변환 전에 실행해 운영 콘텐츠의 잘못된 참조를 차단한다. 한국어 초안 검토에서는 `content:glossary -- --drafts`를 별도로 실행한다.

의미 품질인 목차 대표성이나 독자 관점 평가는 자동 점수화하지 않고 작성·개선 가이드의 검토 단계에서 확인한다.

## 완료 조건

- 가이드에서 목차 제목 규칙과 네 독자 관점 검토 절차를 찾을 수 있다.
- 작성자가 `term` directive와 중앙 용어집만으로 해설을 추가할 수 있다.
- 잘못된 키와 번역 누락이 자동 검증에서 발견된다.
- 웹에서는 말풍선, 터치 환경에서는 하단 패널이 표시된다.
- 마우스 없이도 열기와 닫기를 수행할 수 있고 접근성 관계가 전달된다.
- 260703, 260704, 260705 한국어 초안이 새 목차 및 검토 규칙을 통과하고 필요한 용어 해설을 사용한다.
- 운영 중인 260703과 기존 번역 데이터는 한국어 원고 승인 전까지 변경되지 않는다.
